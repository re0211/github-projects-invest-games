### 2. Claude Managed Agents 的内置记忆（Memory Stores）—— 记忆被挂成文件系统
- URL：https://dev.to/sangrokjung/claude-managed-agents-now-have-built-in-memory-rakuten-cut-first-try-errors-by-97-bd7
- 来源 / 日期：DEV Community；功能 **2026-04-23 Public Beta**
- 是什么：记忆不再是 RAG 栈，而是**挂进会话容器的目录** `/mnt/memory/{store-name}`，agent 用普通 Read/Write/Bash 操作。单个记忆文件 **≤100 KB（约 25K token）**；每次变更生成**不可变版本，留 30 天**；并发写用 **`content_sha256` 前置条件**做乐观锁（哈希不匹配就重读重试）；挂载路径/权限/说明自动注入 system prompt。生产数字：Rakuten 首次通过率错误 **−97%**、成本 **−27%**、延迟 **−34%**；Wisedocs 文档校验快 30%；Netflix 省掉了手动更新 prompt/skill。
- ⚠️ **安全坑（本路最该抄进我们制度的一条）**：默认权限是 `read_write`，而**任何不可信输入（网页内容、第三方工具输出、用户粘贴）都可能被写进记忆，下一次会话当成可信参考资料读出来** —— 这类 bug 在开发环境里不会出现。官方建议：agent 不需要写的 store 一律 `read_only`。另外 store **只能在会话创建时挂载**，运行时不能增删。
- 信号类型：官方功能 / 安全事故（结构性）
- **可复用性：落地（制度层面）。** 我们 `mistakes/` 的**抗污染**现在只做到"每条声明 scope"（`memory_health.py` R5 绿）。按这条，应该再加一条硬规矩：**外部抓来的内容（网页、帖子、别人仓库的 README）不得直接写成记忆条目**，必须先经人确认或标注来源可信度；以及**记忆条目要带内容哈希 + 不可变版本**，改就是新增版本而不是原地覆盖。
- 去重核查：`Memory Stores` / `Managed Agents` / `content_sha256` / `Rakuten` 四份基线 **0 命中**。

### 6. 半百万 token 的上下文，仍然需要一个索引
- URL：https://dev.to/codecoradev/half-a-million-tokens-of-context-still-needs-an-index-351
- 来源 / 日期：DEV Community（引 r/LocalLLaMA 与 HN 讨论）；**2026-09 上旬**
- 是什么：有人在**两张 3090** 上跑 Qwen 3.8 27B、**524,000 token 上下文**，实测 **60–88 tok/s**。作者的回答不是"长上下文杀死了 RAG"，而是 **"哪一层承担成本"**：Transformer 推理对上下文是**线性**的 —— prefill 读全量、KV cache 全驻显存、每生成一个 token 全部重读一遍，**即使答案只要三段话**；检索正相反：索引建一次，每问只读少数块，**成本随"取了什么"涨，不随"拥有什么"涨**。还给了被忽略的成本层 —— **embedding 存储**：768 维 f32 = 3,072 字节/条，**百万块 = 3.07 GB**（还没算副本）；他们自己的 `vecq`（免训练标量量化，默认 5-bit）把百万块压到 **642 MB（4.78×）**，recall@10.979、3.21 ms/query；4-bit 是 514 字节/0.958。**诚实的反例**：某欧洲银行 2026-03 的对照实验中，**单文档简单查询上长上下文准确率高 34%** —— 当每个问题真的需要整篇文档时，全塞进去赢。失败模式是**把 524k 窗口当成所有任务的默认容器**。
- 信号类型：测评数据 / 方法论
- **可复用性：落地。** 三个可直接用的数字：①我们 `index.html`（1.75 MB HTML）**不适合"整篇塞进上下文"**，它是"拥有物"而不是"每问必读"；②"成本随取用涨"就是我们把索引做成**可 grep、可分片、带锚点**的正确性依据；③"单文档简单查询长上下文 +34%"提醒我们**别一刀切**（一次只查一份文件时，整份读进去反而对）。
- 去重核查：`vecq` / `524` 组合（`524` 在 index.html 的 2 处命中为无关卡片数字）**0 命中**。

### 7. 给长跑本地 LLM 的上下文预算算法（llama.cpp 实测，7k–15k/轮）
- URL：https://note.com/kihaya/n/n5de1f2f04839
- 来源 / 日期：note.com（日文，英文版页）；**2026-09 上旬**
- 是什么：作者给长跑本地 LLM 设计了一套上下文预算算法，实测：llama.cpp 侧分配 **131,072 token**，但**每轮实际只送 7,000–15,000 token（限值的 10–15%）**，**跑了 50 轮也和第 10 轮没差别**（无线性增长）。四条核心：①**不总结对话历史** —— 改为**每轮重读工作树当前内容**，历史里的旧工具结果**只替换内容、保留位置**；②**不变项放前、变化项放后**（state block 紧跟 system prompt，验证结果与重贴内容放 footer，**这样 prompt cache 才生效**；内容相同就保证字符串完全相同）；③超预算时**删"最近没碰过"的，不是删最大的**，而且**不是真删 —— 缩成只剩定义行 + 行号的骨架**；④到阈值时**一次性砍到下限**，之后只追加，**绝不从头截断**。战果：棋引擎 52 轮 / 3 小时 28 分 / 17 个测试 / **perft 五组数字全对（20/400/26/5/7）**，全程 **0 次事实性错误**（没调用不存在的方法、没谎称写过代码）。
- 信号类型：方法论 / 测评数据
- **可复用性：落地（本路最可操作的一条）。** 我们现在维护 `index.html` 与长文档时的做法是"开新会话 + 贴摘要"，按这条应该改成：**每轮重读目标文件的当前真实内容（而不是引用历史里贴过的旧版本）+ 把验证输出放在 prompt 末尾 + 淘汰按"最近是否碰过"而非"体积"**。第 ③ 条"骨架化而不是删除"尤其适合我们的**长 md（房规/原则/汇总）**：压缩时保留条目编号与标题、只砍正文。
- 去重核查：`kihaya` 四份基线 **0 命中**。

### 8. 本地 27B 做游戏：一张 4090 上的 23.80 GB 是怎么分配的
- URL：https://note.com/made_from_fuji/n/ne0a9d6f0799e
- 来源 / 日期：note.com 转述 r/LocalLLaMA 帖（**2026-08-30**，1,546 分 / 266 评论）
- 是什么：有人用**单张 4090 + Qwen3.8-27B（Unsloth Q4_K_S）**，7–8 小时做出一个 Three.js 浏览器游戏（模型直接写 `index.html`/`game.js`/`sounds.js`，还生成了音效和 3D 模型代码；加了多管火箭、可做特技的滑板、FPV 无人机、游戏内电脑）。**设置屏上的五个决定**：上下文 **144,369**（模型上限 262,144 的一半）、KV cache **K/V 都是 Q8_0**、**Flash Attention 开**（不开就不能量化 V 侧缓存）、**GPU offload 65 层全上**、量化 Q4_K_S —— 合计**预计占用 23.80 GB**，离 24 GB 只剩 0.2 GB。顺序是**倒推**的：先定要 144k 上下文 → 降到 Q4_K_S → 还不够 → 再把 KV 压 Q8。harness 用 **DSH 的 minimal mode**（工具与工具调用都比标准模式少 → 省上下文；标准模式下 144k 经常干到一半撞上限，minimal 很少撞）；**thinking effort = medium**（只有诊断性能问题时才用过一次 xhigh）；生成速度 **55 t/s**；换更大的 Qwen Next 在同一张卡只有 **7 t/s**（7–8 小时要乘 7），不现实。

- **可复用性：落地（算术可借，结论要改）。** 我们有 16GB **系统内存**、没有 4090；但**"倒推分配"的方法**完全适用：先定上下文长度 → 定量化档 → 再压 KV cache → 最后才谈速度。另外两条立刻可用：**给本地模型关思考（medium/off）而不是 xhigh**；**harness 用"少工具少调用"的 minimal 档**能显著降低撞上限概率 —— 这与我方 `ccgs-cn-config` 里"关思考靠桥注入"是同一件事，现在有了第三方实测背书。
