- 讲了什么：**中文互联网上少见的、由大厂引擎组写的 Live2D 工程落地文档**，三块：
  ① **Live2D vs Spine 选型**（拿真实项目举证）：金亨泰《天命之子》是 Live2D，但新作 **NIKKE 改用 Spine**，原因是「Live2D 的性能消耗和制作成本都大于 Spine，战斗场景过多动态 2D 手机扛不住」；《碧蓝航线》《少女前线》交互立绘用 Live2D；《公主链接》《明日方舟》Q 版用 Spine。技术差异点破得很狠：**Spine 无变形器概念、只有网格顶点，做转向透视时效率低于 Live2D**；**Live2D 的「胶水权重」只能作用于相邻两个旋转变形器，而 Spine 自动权重会计算所有选中骨骼**，所以头发/飘带这类「多骨控一层」的场景 Spine 更自然；并给了个能直接用的判据 —— **参数个数为 n 时，表情复杂度可达 2ⁿ**。
  ② **原画拆分规范（对画师直接可执行）**：**画布尺寸**先定死 —— 以华为 Mate60 Pro 全屏 2720×1260、台式 4K 3840×2160 为参照，**角色高度 > 3000px、建议画布高度 > 4000px**，官方示例工程是 **5800×8400**，原则「宁可大图缩小，不小图放大」；脸部/眼球/睫毛/嘴巴/头发/前后片/阴影逐项给了规范与**常见错误清单**（眼球「眼白范围不足/有透明度/被眼睑遮挡处色差」、嘴巴「上下口片嘴唇长度要一致否则强行拉伸」、头发「要画出被前发遮住的侧发」——举证 **腾讯 VUP 星瞳** 转向时露出多个侧发图层）；阴影必须**整片阴影都画**、不可只画半截；补色层在 Live2D 中**直接禁止**（不同图层晕染会导致「动手臂时腿上的高光跟着动」）；交付前整理规范含「**图像的左侧是角色的右身，应以 R 为后缀**」「建正中垂直参考线，眉心/鼻尖放中位线」。
  ③ **Unity 落地问题**：**动态渐变减弱**（渐变时参数值 A+B 叠加，本该闭眼却半睁）与**渐变穿帮**（官方虹色 Mao 切换时「爱心倒画」），解法是 Live2D SDK for Unity 的 **MotionFade** —— 可分设淡入/淡出时间，还能逐 Live2D 参数设淡入淡出与曲线。
- 可复用性：✅ 落地。理由：**这是本轮最贴你目标（Ren'Py 视觉小说立绘）的一条** —— 它把「立绘该画多大画布」「脸/眼/嘴/发/阴影该怎么拆才不出血」「哪些图层效果在 Live2D 里是禁的」全部落成可执行规范，可以直接抄进你自己的立绘规格书；且「参数 n → 表情 2ⁿ」和「渐变减弱/穿帮」是你将来做表情切换时的现成预警。Unity 那节原理可平移到任何按参数插值的引擎。

### 求助：八月社「あいりすミスティリア」角色表情差分该怎么合成拼接（含 opencv 对齐脚本）—— Live2DHub 论坛 / 楼主 xxx1、回帖 VivaLaze 等 / 6月20–22日（年份未核实）
- 链接：https://live2dhub.com/t/topic/6117/3
- 核实：**已打开页面**。楼主 **xxx1** 于「6月 20 日」发布，回帖 **VivaLaze**「6月 21 日」、**SakuraClover**「6月 22 日」、**nozomi**「6月 22 日」——**页面只显示月日、不含年份，年份未核实**。附件 `emo_face_match.zip`（1.5 KB）真实存在并可下载，脚本正文在页面上完整可见。
- 讲了什么：楼主想**用 Ren'Py 做一个 Live2D 立绘播放器**，卡在「表情差分怎么跟身体拼接 + 拼好后在 Ren'Py 屏幕里怎么定位」。回帖给了两条可抄的路线：
  ① **VivaLaze 的 opencv 对齐脚本** `emo_face_match.py`（依赖 `opencv-python numpy`）：用 `cv2.matchTemplate(full, face, cv2.TM_CCOEFF_NORMED)` 求「表情差分小图」在「身体大图」中的左上角偏移 `(x, y)`，匹配度 < 0.8 时告警；再把子图用**透明像素 padding** 到与大图同尺寸的 BGRA 画布、按偏移贴上并输出，同时把偏移写进 `match_log.log`。前置约束：**要求差分图是身体图上某区域的精确裁剪（尺寸一致）**，且**输入路径避免非西文字符**（终端字符集会报错）。顺带纠正一个常见误解：**Ren'Py 加载前会把图像剪裁到非透明像素包围盒（bounding box），所以创作者自己裁图不会提升性能也不会减小图尺寸**。
  ② **nozomi 的「别把简单事复杂化」路线**：差分（纸娃娃）优先用 Ren'Py 的 **`layeredimage`**（新手册也推荐，但**必须先定义所有角色的所有参数**，角色一多就「做到怀疑人生」）；静图则给了一段 **`im.Composite`** 的 label 用法示例（`im.Composite((1058,1256),(0,0),"stand.png",(499,89),"default.png")` + `pos(.5,100) xanchor(.5)`）。另有 SakuraClover 提出「数据一多 Ren'Py 进去巨慢，改用 nw.js，秒加载，spine/live2d/图片帧都支持」。
- 可复用性：✅ 落地。理由：**你正是「目标 Ren'Py + 要拼表情差分」的人**，这条把两个具体问题（差分对齐偏移、屏幕定位）都给了可直接跑的代码 —— 那个 opencv 脚本能一键算出每张差分相对身体的 `(x,y)`，正好喂给 `im.Composite` 的坐标位；`layeredimage` 那条则给出「要不要用、什么时候会失控」的判据。
- ⚠️ 疑点：脚本自带 `print("警告：匹配度{max_val}较低")` —— **f-string 漏了 `f` 前缀**，那句永远不会插值、只会原样打印 `{max_val}`；属于作者笔误，抄用时需自己补 `f`。**不是编造功能**，只是代码 bug。

### 【开源】在 Bianbu 桌面上养一只真正可用的 Live2D 桌宠 —— 进迭 RISC-V 论坛 / 作者 chenjiayi / 2026-08-30
- 链接：https://forum.spacemit.com/t/topic/1621 （仓库：https://gitee.com/achenjiayi/rv_ive2d_pet ，分支 k3_dev，Release v0.3.18）
- 核实：**已打开页面**。作者 **chenjiayi**，发布时间显示「8月 30 日」（页面未给年份，正文首页时间轴为 2026-08-30，据论坛当前年份推定 2026-08-30，**年份未核实**）。正文内给出真实数字：`.deb` 版本 `live2d-web-pet_0.3.15` → 正文末尾更新到 **0.3.18**；点击穿透更新频率 **约 8 Hz**、**4× 降采样**；支持 **Cubism moc3 v2–v5**，**Cubism 2 的 `.moc` 不兼容**；内置模型 **haruto / Furina / Diana** 三个；K3 算力「60T」可跑「最大 30B LLM」。
- 讲了什么：一条**在 RISC-V 开发板（SpacemiT K1/K3 + Bianbu LXQT + Wayland）上跑通 Live2D 桌宠**的完整工程记录。核心架构是「**Cubism Web Runtime 画 → Headless Chromium 出 RGBA 帧 → GTK Overlay 贴桌面**」，用 `gtk-layer-shell` 落在 Wayland 上。关键技术点：① **透明区域点击穿透** 靠逐帧 RGBA 做 Alpha 分析、只把角色不透明区注册为输入 region（不额外开第二条 GPU 管线）；② 明确踩坑 —— **Cubism Native SDK 没有 RISC-V 官方档位**，且 **moc3 受版权保护不能逆向拆解**，所以绕开 Native SDK 走 Web；③ Wayland 与 X11 并存时 GTK3 会误走 X11 导致 layer-shell 假成功 + compositor 疯狂 CRITICAL，解法是显式 `GDK_BACKEND=wayland`；④ 模型包很乱（VTube Studio 工程、`(1).json`、重复文件、Idle 指向 Scene 演出动作），于是做了「导入器 → `pet_meta.json` → `models.json`」的显式导入边界，避免「开机突然自己开始谢幕」。
- 可复用性：🔶 参考。理由：**技术栈（Wayland/GTK/RISC-V）与你的 Windows+Ren'Py 完全不同，不能照抄**；但「透明点击穿透靠 Alpha region」「Cubism Native 无 arm/riscv 档、moc3 不可逆向 → 绕道 Web」这两条判据，对你判断「Ren'Py 走 Native 还是 Web」有旁证价值，且它证明 `moc3 v2–v5` 单运行时可以通吃。
