## 本辑一句话

**成本不是被省掉了，是被挪到了"输入侧"和"半年后"。**

三条独立线索收敛到同一件事：

1. **长会话的账单几乎全在输入侧，所以缓存命中率是唯一真杠杆。** 一手 DSH 两个会话的账是
   **输入 57.5M / 输出 151K（约 380:1）**、缓存命中 **99%**；88 页论文任务是 **输入 6.6M / 输出 72.7k**。
   AI NPC 侧同样形状：**一次对话输入约 1,500 token、输出约 150 token**。
   结论很硬：**裁剪输入（上下文、记忆摘要、历史）比限制输出重要一个量级**——而前缀顺序排对就能把命中率做到 70%~90%。
2. **"写代码"只占一个功能的 25%，AI 恰好只压缩了这一环。** 100 小时 = 25 小时写代码 + 75 小时其余；
   《镜海》三个月的一手时间账是**审查与测试 45% + debug 25% = 70%**，净节省只有 **30%~40%**。
   于是出现两组打架的数字：4867 人的现场实验 **+26%**，16 名资深开发者的 RCT **-19%（但体感 +20%）**——
   而 **69% 的人照旧续费**。
3. **代价出现在第 6 个月之后。** 四阶段轨迹的第 12–18 个月是"**维护成本增长到传统代码库的四倍**"，
   且**入职时间不降反升**（架构是从数百次独立会话里"涌现"的，不是设计出来的）。

最值钱的三条：**§10《镜海》的时间账与那起 40 分钟的并行会话覆盖事故**、**§11 的前缀顺序（最便宜、最好验）**、
**§16 的四阶段维护陷阱时间轴 + "全局改名"判据**。

## 一、上下文管理 / 长会话 / 记忆与交接（第一优先）

### 1. Vibe Coding 实战：自然语言驱动开发与全局文档工作流（CSDN）
- 链接：https://blog.csdn.net/weixin_29055699/article/details/165636778
- 来源 / 日期：CSDN · 作者 weixin_29055699 · 原创 **2026-09-16 14:17**（212 阅读）
- 一句话：vibe coding 的分水岭不在选哪个工具，而在有没有一份"少而硬"的全局 md 文档在替你守边界。
- 关键点：
  - **反直觉的实测结论**：作者最初写了**两千行 GLOBAL.md**，结果 AI"需要在大堆规则里找相关条目，反而频繁误读、逻辑混乱、对话质量直线下降"；改成 **50 行以内只写硬约束**后才正常。判据是「少而硬，不要多而软」。
  - **Builder 模式无限循环**：亲眼看着 AI **自己重试了 8 轮 npm install** 仍失败，最后靠人工锁版本才解决。处置动作是**打断循环 → 问它"你刚才尝试了什么/失败原因/最可能的根因"**，而不是让它继续蛮干。
  - **换工具即失忆**："AI 的记忆只存在于当前会话"，换工具/切模型/关窗口全没。做法是**每个关键决定无论大小都同步到 `docs/architecture.md` 或 `docs/roadmap.md`**；新会话开头固定一句"请阅读 GLOBAL.md 和 docs/architecture.md，不要修改它们"。
- 可自测点：
  1. **GLOBAL.md 长度对照实验**：同一任务分别用 50 行 / 300 行 / 2000 行规则文件跑，记录 AI 误读次数与首版可用率——验证"少而硬"是否真优于"多而软"。
  2. **依赖锁版本**：故意不让 AI 写 lockfile，跑两次新建项目，比对两次装出的依赖树差异（可复现"每次装出不同结果"）。
  3. **跨工具失忆**：同一个任务在 Claude Code 与另一工具间切换，测量"不落盘文档"与"落盘文档"两种情况下恢复上下文所需的轮数差。

### 2. Vibe Coding 实战：从零构建完整项目的关键工作流与避坑指南（CSDN）
- 链接：https://blog.csdn.net/weixin_42573647/article/details/164790093
- 来源 / 日期：CSDN · 作者 weixin_42573647 · 原创 **2026-09-09 16:26**
- 一句话：把"写完整项目"拆成骨架先行 + 小步迭代 + 每步可运行，并给出一张 6 行"症状→原因→解法"排障速查表。
- 关键点：
  - **上下文漂移的量化场景**：作者明确描述"**第 30 轮**让它给列表页加筛选，它已经忘了最开始定的"技术栈是 Vue3 不是 React""。三条对策：每个新主题开新对话 / 新对话开头带一份"**项目背景快照**"（技术栈 + 目录结构 + 当前任务 + 上一步进度）/ 核心约定写进 `.cursorrules`。
  - **四步需求拆解 + `docs/plan.md`**：描述最终形态 → 拆主干路径（**十个节点以内**）→ 列技术边界（连版本号都写死，例"Next.js 14.2、React 18、TS 5.6、Tailwind 3.4，禁止使用 app router 未稳定 API"）→ 排优先级。plan.md 兼作"每个对话的大上下文"。
  - **"给 AI 建立失败记忆"**：修完一个 bug 后明确告诉它"这个文件之前出现过 xx 问题，今后遇到 xx 情况优先用 yy 方案"，**每隔几轮固化一次**，作者称"同一个项目里表现会肉眼可见地变好"。
- 可自测点：
  1. **项目背景快照有效性**：开两个新会话跑同一需求，一个带快照一个不带，比对首次输出命中技术栈的比例。
  2. **每步可运行 vs 一次性生成**：对比"骨架→小步"与"一次性生成 20 文件"两种方式到首个可运行状态所需轮数与报错条数。
  3. **失败记忆固化**：在同一项目里连续 5 次触发同类 bug，测"固化/不固化"两组的复发次数。

### 3. 试用 DeepSeek Harness 的几个意外发现：缓存命中率 99%（微信公众号）
- 链接：https://ima.qq.com/wiki/?shareId=ee2481cbd89f73301a9babcc27c00ed5a25eb5a587fa69182cf1589b9b3c978d&mediaId=wechatarticle_672ba56fbee938f538d7c9e042252381_67c021ab4cff0672c6e76705a19a6e347466449362753872&action=openDetailDrawer&webFrom=10000171
- 来源 / 日期：微信公众号「着眼于长期价值」· **2026 年 8 月 22 日 01:56**（上海）；经腾讯 IMA 知识库检索到全文
- 一句话：一手跑了两整天 DSH，两个会话的缓存命中率都是 **99%**，对比 Claude Code + DeepSeek 官方 API 的最高 **97.8%**。
- 关键点（**两个会话的完整统计，是他最硬的账**）：
  - 会话一：**18 轮 / 316 步 / LLM 30m25s / 工具调用 30m31s / 首 token 平均 2.2s / 136 tok/s / 缓存命中 99% / 输入 57.5M tok / 输出 151K tok**；
  - 会话二：**13 轮 / 175 步 / LLM 20m4s / 工具调用 8m14s / 首 token 2s / 140 tok/s / 缓存命中 99% / 输入 27.3M / 输出 117K**；
  - 注意这个比例：**输入 57.5M 对输出 151K（约 380:1）**——长 agent 会话的账单几乎全在输入侧，缓存命中率是唯一真正有效的杠杆。
  - 另外两点：DSH **原生支持一键切换大模型供应商与模型**；定制性强，"哪里用着不满意就直接改"。
- 可自测点：
  1. **缓存命中率对照**：同一任务分别在 DSH 与 Claude Code+DS API 上跑，记录命中率差（他测的是 99% vs 97.8%）与**输入/输出 token 比**。
  2. **380:1 的输入输出比**是否在我们的索引站维护任务里也成立（若成立，则"压缩输入"比"限制输出"重要一个量级）。
  3. **换供应商不换 harness**：验证"一键切换模型供应商"是否真的不需要改任何业务代码。

### 4. 实测 DeepSeek Harness："一切皆插件"设计（虎科技）
- 链接：https://m.hukeji.com/ruanjian/202608/137853.html
- 来源 / 日期：虎科技（hukeji.com）· **2026 年 8 月**
- 一句话：88 页论文翻译任务一手计时数据——**22 分钟、首 Token 平均 1.4 秒、缓存命中率 98%、输入 6.6M、输出 72.7k**，派发 10 个子代理。
- 关键点：
  - **四种模式各自默认加载不同插件集**：标准（完整工具组合）/ **PTC**（程序化工具调用，由模型生成一段代码组合多轮工具调用）/ **极简**（**只保留 1 个 shell 工具 + 1 个文件编辑工具**，专为最小环境下的模型基准测试设计）/ 创造（检查运行时、在内存中试验 Cordis 插件并组合出新模式）。
  - **极简 vs PTC 写贪吃蛇的对照**：极简模式 **50 多秒**完成但**产出是 Python 脚本不是 HTML**；PTC 模式 **1 分 05 秒**。**极简模式明确"不做多余动作"**——它的设计目标是给模型跑分，不是给人用。
  - **"轨迹"设计**（同题另一篇提到）：系统提示词、思维链、工具调用结果、子 Agent 调度、每次上下文注入**全部写入会话日志，只追加不删除**，支持恢复与分叉回放。
- 可自测点：
  1. **极简模式当作模型基准的对照环境**：用同一道编程题在极简/标准/PTC 三模式下跑，比对耗时与产物形态差异（这是很少见的、厂商自己提供的"最小干扰"测试床）。
  2. **PTC 模式**是否真能减少工具调用轮次——同一任务跑 PTC 与标准模式，比对轮数与总 token。
  3. **轨迹日志体量**：跑一个长任务后看只追加日志涨到多大，评估长期维护成本。

### 5. 国产大模型竞争逻辑从拼价格转向拼生态（证券日报）
- 链接：https://www.cet.com.cn/wzsy/cjcj/10557981.shtml （中国经济新闻网转载版，同题另见中国网 finance.china.com.cn/industry/20260915/6324290.shtml）
- 来源 / 日期：**证券日报** · 记者袁传玺 · **2026-09-15 08:23**
- 一句话：9 月国产模型密集调价，出现**同时提价与降价**的"梯队分化"，同一任务选不同模型成本差距接近 **60 倍**。
- 关键点：
  - **降价侧**：**9 月 10 日 12 时起** DeepSeek 下调 Flash 系列，**闲时输入（缓存命中）从 0.05 元/百万词元降至 0.02 元/百万词元，降幅 60%**；8 月 26 日智谱开源 GLM-5.3-Flash（旗舰版十分之一定价）、阿里开源 Qwen3.8-Flash（官方称最低可至 DeepSeek V4 Flash 的三分之一）。
  - **涨价侧**：智谱 GLM Coding Plan 新版订阅 **Lite/Pro/Max 月费由 49/149/469 元涨到 118/538/1078 元，三档分别上涨约 141% / 261% / 130%**——理由是智能体应用增长推高算力压力、长上下文请求高度依赖缓存。
  - **梯队分化**：经济型模型输入普遍降到 **1 元/百万词元左右**；旗舰端 **Kimi K3 输入 20 元 / 输出 100 元**，而 **MiniMax M3 "永久五折"后仅 2.1 元 / 8.4 元**。中国电信研究院预计 **2026 年我国词元年消耗量将达 10 亿亿**。
- 可自测点：
  1. **闲时/忙时定价套利**：把批量、非实时的索引更新任务挪到闲时段，实测账单降幅是否接近文中 60%。
  2. **同一任务跨模型成本对照**：固定一个我们自己的典型任务（如"读 20 个仓库 README 写摘要"），在 Kimi K3 / MiniMax M3 / DeepSeek Flash 上各跑一次，验证"60 倍差距"在真实任务上的量级。
  3. **订阅制 vs API 制**：GLM Coding Plan 涨价 141%~261% 后，按月用量反算哪种更划算——这条直接决定我们要不要续订。

### 6. Claude Code 用了 1 个月，我把成本压到官方价格的 1/5（稀土掘金）
- 链接：https://juejin.cn/post/7631852793092112384
- 来源 / 日期：稀土掘金 · **2026 年实测**（标题自带年份）
- 一句话：把降本拆成四层叠加，逐层给出相对官方价格的百分比——**上下文管理只是最后一层，贡献约 30% 输入量削减**。
- 关键点（**这是本辑唯一给出"逐层叠加百分比"的账**）：
  - 四层叠加表：官方 API 直连 **100%** → 低汇率中转站 **≈33%**（内部汇率 ¥2.4/$）→ +Prompt Cache **≈16%**（输入端 60% 命中、读取成本降 90%）→ +effortLevel medium **≈12–13%**（输入 token 再减约 25%）→ +`/compact` `/new` 管理 **≈8–10%**（上下文缩短，输入量再减约 30%）。
  - 前提假设全部写明：输入/输出权重 30/70、Cache 命中率 60%、effortLevel 节省 25%、上下文管理节省 30%，且均为输入端。作者明说"实际效果因使用场景而异"。
  - 使用节奏一条线：`开始任务 → 正常对话 → 上下文变长时 /compact → 任务完成或切换话题时 /new`；称单靠上下文管理可让**每次请求的输入 token 减少 30–50%**。
- 可自测点：
  1. **单独验证最后一层**：不改汇率、不改模型，只做 `/compact` + `/new`，看我们自己的会话输入 token 是否真降 30–50%（这一层是全表唯一与"钱无关、纯工程"的）。
  2. **`/compact` 的收益是否被高估**：压缩本身要花一次输出 token 去做摘要，短会话里可能倒亏——测出我们任务的**压缩盈亏平衡点**（多少轮之后压缩才开始净赚）。
  3. ⚠️ 前两层（低汇率中转站）涉及**灰色渠道**，不建议采用；只取后两层。

### 7. 用了半年 AI 编程，我的手写代码能力退化了多少？（稀土掘金）
- 链接：https://juejin.cn/post/7629290989707345935
- 来源 / 日期：稀土掘金 · 作者自述"半年"重度使用后的**关掉 AI 实测一天**
- 一句话：关掉 AI 干一天，效率掉约 70%，五个任务只完成三个半——并给出可对照的「5 个退化征兆」清单。
- 关键点：
  - **一天的实测账**：上午卡在 SwiftUI `refreshable` 修饰符位置（放错三次）、`ScrollView` 套 `LazyVStack` 还是 `List`、`NavigationStack` 怎么嵌套；下午修分页重复数据 bug，**一行一行断点追了两个小时**（以前丢给 Claude 30 秒定位到 offset 计算逻辑）。
  - **五个退化征兆**（自评"中三个以上说明已在退化"）：① 记不住 API（`jwt.encode(payload, secret, algorithm="HS256")` 参数顺序混、`algorithm` 拼写犹豫）② 写不出算法（二叉树层序遍历，队列初始化写错、层级计数逻辑反了）③ 另有三个见原文。
  - 作者自我定位在「B 和 C 之间」：**能写，但很多细节卡得痛苦**；比喻是"每天开自动挡的老司机被扔了一辆手动挡——不是不会开，是肌肉记忆没了"。
- 可自测点：
  1. **"关掉 AI 一天"自测**：固定一组我们自己的日常任务（写脚本 / 改 HTML / 查 bug），分别在开/关 AI 下计时，测真实掉速比是否也接近 70%。
  2. **退化征兆清单对照**：五条里命中几条，命中即说明该模块应恢复手写。
  3. **反制方案**（与 §12 同向）：核心模块刻意不用 AI、让 AI 从"替你写"变"替你审"。

### 8. Claude Code 上下文压缩与新对话指南（稀土掘金）
- 链接：https://juejin.cn/post/7655151256498978842
- 来源 / 日期：稀土掘金
- 一句话：把压缩时机落到"阶段边界"上，并给出三种典型故障（溢出 / 压缩丢信息 / 对话混乱）的症状与解法。
- 关键点：
  - **分阶段压缩**（每阶段保留什么写死）：阶段 1 需求讨论完成 →`/compact 保留需求分析结论和架构决策`；阶段 2 设计完成 →`保留设计方案和接口定义`；阶段 3 实现中途 →`保留当前实现进度和已知问题`。
  - **任务分解模板**：大型任务拆成子任务 1/2/3，**每个子任务一个专门对话，完成后 `/clear`**，而不是一条长对话走到底。
  - **三类故障速查**：溢出（症状=响应变慢、工具调用失败 → 及时压缩）／**重要信息被压缩丢失**（预防=带提示词压缩 `/compact 保留数据库 schema 设计和 API 端点列表`；补救=关键信息写入文件 + `/memory` 保存决策）／对话混乱（症状=理解偏差、回答不相关 → `/clear` 后重新描述任务）。
- 可自测点：
  1. **带焦点压缩 vs 不带**：同一会话分别跑 `/compact` 与 `/compact 保留 X、丢弃 Y`，比对压缩后"需要重读的文件数"——验证"定向压缩能减少多少回读"。
  2. **子任务分对话 vs 单长对话**：同一个多步任务两种方式各跑一次，比对总 token 与最终正确率。

## 五、游戏制作 × AI（一手长线复盘）

### 10. AI 辅助开发三个月：《镜海》核心玩法跑通与代码审查实战总结（CSDN · 系列第 07 篇）
- 链接：https://blog.csdn.net/weixin_31556767/article/details/164441390
- 来源 / 日期：CSDN · 作者 weixin_31556767 · 原创 **2026-09-06 11:50**（系列第 07 篇）
- 一句话：一个人用 AI 做俯视角 roguelite 三个月、约 9000 行代码、AI 生成占比超七成——**但净节省只有 30%~40%**，因为审查+debug 吃掉了 70%。
- 关键点（**时间账是本辑游戏侧最硬的一手数据**）：
  - **一个多月的时间记账**：需求描述 + Prompt 编写 **15%** / AI 生成代码后的**审查与测试 45%** / **Debug 和兼容性修复 25%** / 逻辑设计与其他 **15%**。结论：**代码书写时间从 50% 降到不到 10%，但审查与测试大幅增加，两相抵消后实际节省约 30%~40%**。
  - **回滚事故（值得单独记）**：在 Cursor 里**同时开两个会话**分别写"道具拾取"和重构"角色属性管理器"，**两者都改了 `player.gd` 且没用分支** → 后保存的覆盖先保存的 → 运行报 `Attempt to call function 'add_bonus' in base 'null instance'`；**排查耗时约 40 分钟**，期间已动了重写存档系统的念头。事后硬性规定：**同一时刻只允许一个 AI 会话修改同一个文件**；所有 AI 生成代码纳入 Git。
  - **"AI 生成"≠"AI 生成后能进游戏"**：五步接入流程（需求拆到"停顿 0.3 秒 / 冲刺速度 400 / 持续 0.5 秒"这种粒度 → 不审查不上线（重点查变量作用域、是否改全局状态、**物理体运动是否放 `_physics_process` 而非 `_process`**）→ **单独建 `test_combat.tscn` 最小场景**（只放一个玩家、一个敌人、一块平地）→ 整合进主场景（最容易踩的是 Area2D 在场景切换后被提前释放）→ **每天 30 分钟代码清理**统一命名）。
  - 选型理由很实在：Godot 4.2 因为"**GDScript 简单，没有复杂泛型、没有层层接口继承，AI 不需要理解太多上下文**"；作者的开发机是"几年前的笔记本，跑 Unity 风扇狂转"。
- 可自测点：
  1. **时间账复刻**：给自己的 AI 辅助任务按同样四分类记一周时间，看"审查+debug"是否也占到 70%——这直接决定我们对 AI 的期望值设在哪。
  2. **并行会话冲突**：故意开两个会话改同一文件重现覆盖事故，验证"单会话单文件"规则的必要性（**这条可直接写进房规**）。
  3. **最小测试场景**：为自己项目建一个只含 2~3 个节点的隔离场景，统计"在小场景发现的问题数 / 进主场景后才暴露的问题数"。
  4. **每天 30 分钟清理**：评估这 30 分钟是否真能降低后续 AI 生成的代码漂移（文末称"上下文更清晰了，AI 后续生成质量也会跟着提高"）。

## 六、Prompt Cache / Token 成本工程

### 11. Agent 场景下 Token 成本优化的实战技巧（稀土掘金）
- 链接：https://juejin.cn/post/7679973154161426442
- 来源 / 日期：稀土掘金
- 一句话：三招立省 50% 且零架构改造——**前缀顺序、模型分层路由、中文任务用中文原生模型**。
- 关键点：
  - **前缀匹配是硬机制**：只有当本次请求**前 N 个 Token** 与之前某次完全一致，缓存才命中。作者点名"很多团队第一版 Agent 都踩了这个坑：把用户数据放最前面、固定内容放后面，结果缓存完全失效"。正确顺序 `System Prompt(固定) → 工具描述(固定) → 历史对话(半固定) → 用户消息(变化)`，反过来则"哪怕前面有几千 token 固定内容，一个都命中不了"；排对后**命中率能轻松做到 70%~90%**。
  - **模型分层路由（作者称"性价比最高，没有之一"）**：他们的判责 Agent 里，**主 Agent 负责调脚本、识别诉点、分发任务、生成报告（偏流程化）用 Qwen3.5；子 Agent 负责核心推理与判责用 Qwen3.7-plus**。算账：**主 Agent 占 60% 调用量、模型价差 5 倍 → 光这一项省 50% 以上**。
  - **中文分词器 = 成本项**（最容易被忽略的一条）：中文原生模型（Qwen/DeepSeek/GLM）分词器对中文压缩效率高得多，**可省 30%~50% Token 数量**，叠加单价优势后**总成本可降至 GPT 系列的 1/5 左右**。原理是"中文占比高的训练数据里 BPE 合并频率更高"。
- 可自测点：
  1. **前缀顺序 A/B**：同一批请求，把固定内容前置 vs 后置，直接读 API 响应里的缓存命中字段，量化差距（这是本辑最容易验、也最值钱的一条）。
  2. **分词器对照**：把同一段中文 prompt 分别用中文原生模型与 GPT 系列 tokenizer 计数，验证"省 30%~50%"这个数。
  3. **主/子 Agent 分层**：把我们的编排型任务切到便宜模型、推理型任务留旗舰，测总成本降幅是否接近 50%。

### 12. 从 Prompt Engineering 到 Context Engineering：2026 年 Agent 性能提升的隐藏杠杆（CSDN）
- 链接：https://blog.csdn.net/2301_80370251/article/details/164118136
- 来源 / 日期：CSDN · 作者 2301_80370251
- 一句话：把"缓存友好设计"写成一条可执行的排序规则，并把上下文管理分成**被动压缩**与**主动笔记**两条路。
- 关键点：
  - **各家缓存折扣**：Anthropic 官方称**缓存命中时延迟降低一半以上、成本最高可省 90%，缓存读约为正常输入价格的 1/10**；OpenAI 相同前缀自动命中、命中部分打折；**DeepSeek 提供上下文硬盘缓存，命中时输入成本约降至 1/10**。
  - **缓存友好排序规则**（一句话版）：`system(静态角色+规则) → 检索片段 → 历史 → 本轮任务`；反面是"system 里混入每轮都变的日期/用户信息/临时数据 → 前缀每次都变，永远不命中"。显式点名"OpenAI 需确认实际存在 **1024 token 以上**的重复前缀"（与 §11 的前缀机制互为印证）。
  - **Compaction 是被动的，结构化笔记是主动的**：Agent 把关键状态写到**上下文之外**的文件（`NOTES.md`、to-do list），需要时读回；举例是"Claude Code 维护待办清单、Anthropic 让 Claude 玩 Pokémon 时记账"。价值在于**即使上下文被压缩或重置，关键信息也不丢**。子 Agent 架构则把 context rot "隔离"在子窗口里。
- 可自测点：
  1. **1024 token 门槛验证**：数一下我们 system prompt + 工具定义的稳定前缀有多少 token，不足 1024 则 OpenAI 自动缓存根本不生效——这条决定了要不要为凑前缀而重构。
  2. **主动笔记 vs 被动压缩**：跑一个长任务，一种只靠自动 compact，一种外加 `NOTES.md` 主动落盘，比对任务末尾的"关键决策丢失数"。

### 16. AI 生成代码的维护陷阱：团队在六个月后才发现的真相
- 链接：https://tianpan.co/zh/blog/2026/04/17/ai-generated-code-maintenance-trap
- 来源 / 日期：**2026-04-17**（中文版；行文有译写痕迹，数字需按二手源对待）
- 一句话：给出了 AI 代码库的**四阶段恶化时间轴**，终点是"**维护成本增长到可比传统代码库的四倍**"。
- 关键点：
  - **四阶段轨迹**：第 **1–3 个月**效率显著提升、PR 吞吐量增加、管理层为生产力指标欢欣；第 **4–6 个月**代码审查沦为橡皮图章、死代码积累、**不同会话写的模块呈现不一致的模式**；第 **6–12 个月**重构尝试失败（没人理解完整影响范围）、调试时间增加、构建失败更频繁；第 **12–18 个月**"**维护成本已增长到可比传统代码库的四倍**"，团队无法有把握地交付功能。
  - **反直觉的一条**："**在大量使用 AI 辅助的代码库中，入职时间不降反升**"——与"团队从绿地起步测量效率提升时的预期恰恰相反"。原因是**架构不是设计出来的，是从数百次独立 AI 会话中涌现的**，每次会话内部连贯但全局不一致；新工程师"无法读一个模块然后推断其设计理念，因为根本没有统一的设计理念"，也**无法问作者为什么，因为作者是 AI、那次会话的上下文早已不在**。
  - **对策（生成时捕获意图）**：在接受 AI 代码**之前**记录它想做什么、什么约束塑造了实现——"一个解释非显而易见设计选择的**两句话注释**"就够。学界已把它形式化为"**变更意图记录**"（结构化捕获目标、约束、边界、假设）。
- 可自测点：
  1. **"全局改名"测试**（判据最硬）：在我们的仓库里对一个跨模块概念做一次全局重命名，统计有多少文件跟着变——只有 1 个文件跟着变即说明结构脆弱。
  2. **入职时间探针**：让不熟悉某模块的人（或新会话的 AI）读模块后回答"这个模块的设计理念是什么"，答不出即是理解债务已形成。
  3. **两句话注释**：对最近接受的 10 段 AI 代码补写"为什么这么写"，一个月后回看是否真的降低了返工。

### 18. Claude Code 企业级工程实践：从单点提示到智能体协同（极道 Jdon）
- 链接：https://www.jdon.com/90038-claude-code-system-playbook-enterprise-agents.html
- 来源 / 日期：极道（jdon.com）
- 一句话：把"技能 / 子智能体 / MCP"三件套的**机制级数字**讲清楚了，并点出一条容易被忽略的限制：**子智能体不可嵌套调用**。
- 关键点：
  - **技能（Skills）的省上下文机制**：Claude **仅在启动时加载所有技能的元数据（约 100 token/个）**，只有判定相关时才加载完整内容——以此避免上下文膨胀。作者团队已把该模式扩展到数据库查询模板、API 文档格式、会议纪要生成。
  - **子智能体的规格**：每个子智能体是**独立 Claude 实例，拥有专属 20 万 token 上下文、系统提示与工具权限**；主智能体通过"**委托—汇总**"交互，**主对话只保留摘要而非全过程**。内置 Explore（代码探索）/ Plan（研究规划）/ 通用三类，可自定义（例：`security-reviewer` 限定只能读与搜索、输出按严重等级分类的漏洞清单）。
  - **一条硬限制**："**子智能体不可嵌套调用，确保系统可预测性**"——这条决定了多层委派架构做不了。
- 可自测点：
  1. **100 token/技能元数据**：实测我们的技能库在启动时占多少上下文，验证"渐进式加载"是否真的省（若一次性全量加载，超过 ~20 个技能就开始挤压正文）。
  2. **不可嵌套这条**：验证子智能体里再派子智能体会怎样（报错还是静默降级）——直接决定我们的多层调研架构能不能这么搭。
  3. **只读 reviewer 子代理**：照抄 `security-reviewer` 做法建一个只能读写的审查代理，测它对主上下文的污染程度。

### 19. Claude Code 子代理实战指南：安全委派并行工作（ClaudeCodeLab）
- 链接：https://claudecode-lab.com/zh/blog/claude-code-subagent-patterns/
- 来源 / 日期：ClaudeCodeLab（claudecode-lab.com）· 中文
- 一句话：把"委派"定义成一份**五要素小合同**，并给出两个可抄的代理分工角色（explorer / worker）。
- 关键点：
  - **委派 = 写清一份"小合同"**，五要素：**目标 / 允许编辑的文件 / 禁止触碰的文件 / 完成标准 / 返回格式**。原话："这里的'委派'不是把任务随手丢给另一个 AI"。
  - **两个角色分工**：`explorer` = **只读调研代理**，先摸清范围、**不直接改文件**；`worker` = **只编辑指定文件的执行代理**。另有 **`disjoint write set`（不重叠的可编辑文件范围）** 概念——并行委派的前提是各代理的写集合不相交。
  - **三条实务记住**：子代理有隔离上下文、项目级代理放 `.claude/agents/`、**子代理返回的长结果仍然会占用主对话上下文**（即隔离只对过程有效，对结果无效）。
  - **反面判断**："子代理不是越多越好。**小改动如果也拆出去，每个代理都要重新读文件，反而更慢**"；判断标准是"拆开上下文是否有价值 + 编辑范围能否切得足够清楚"。
- 可自测点：
  1. **写集合不相交**：用两个 worker 并行改**有交集**的文件 vs **无交集**的文件，比较冲突次数——直接验证 §10《镜海》那起覆盖事故（§10 条目 10）的根因。
  2. **返回长度控制**：给子代理限定返回格式（如"只返回 5 行结论 + 改动文件列表"），测主上下文占用降幅——针对"长结果仍占主上下文"这条。
  3. **拆分的盈亏点**：同一任务分别在 1 个 / 3 个 / 6 个子代理下跑，找出"越拆越慢"的拐点。

## 十五、DeepSeek Harness（续）

### 24. 开发 DSH 插件：从最小插件到打包安装（含一个 Git 安装的坑）
- 链接：https://dsh-plugin.org/tutorials/develop-dsh-plugin
- 来源 / 日期：dsh-plugin.org 教程页（另有官方版 deepseek-harness.github.io/deepseek-harness/en/develop/basic/）
- 一句话：插件就是一个导出 `apply` 的 TypeScript 模块，但**打包与安装环节有一个不做就白干的坑**。
- 关键点：
  - **最小插件三行**：`export const name = 'hello-plugin'` + `export function apply(ctx: Context) {...}`。用 `inject` 声明依赖（`export const inject = ['tools']`），框架会**等依赖服务就绪才加载插件**；配置用同名 `Config` 类型 + Schemastery schema，框架在加载时校验并填默认值。
  - **清理是可逆的**：通过 `ctx` 注册的监听器/工具/定时器在插件卸载时自动清理；需要手动清理的资源（如网络连接）用 `ctx.effect(() => { ...; return () => cleanup() })` 返回 disposer。
  - **打包坑（最值得记）**：可分发插件要在 `package.json` 里声明 `dsh.bundle`，配 `cordis.patch.yml`；安装用 `dsh plugin --profile <name> add <path>`，装完**用 `dsh --profile <name> --dump-config` 验层**再启动。**⚠️ 从 GitHub 安装拉的是源码而不是构建产物、且不会跑 build 脚本——TypeScript 包必须自带 `prepare` 脚本**，否则装完是空壳。
  - **隔离边界**：Host 插件不能碰 DOM，Client 插件不能读本地文件，全部数据交换走内部事件总线；**web 与 headless profile 相互独立**，装在 web 的插件不会在 headless 下加载。
- 可自测点：
  1. **`--dump-config` 验层**：把"装完先 dump 再启动"固化为安装步骤，避免装了个没生效的插件还在排查为什么工具没出现。
  2. **Git 安装的 `prepare` 脚本坑**：从一个 TypeScript 插件仓库直接 `dsh plugin add`，验证是否真的不跑构建——这条是**最典型的"README 写了 ≠ 能装"（M-0016）**场景。
  3. **profile 隔离**：同一个插件分别装到 web 与 headless，验证 headless 下确实不加载（决定了我们的插件要装几份）。
