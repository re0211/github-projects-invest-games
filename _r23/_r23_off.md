### 1. arXiv 首次给「coding harness」做组件级消融：上下文管理不是提分手段，是**防溢出保险**
- 链接：https://arxiv.org/abs/2609.20804
- 来源 / 日期：arXiv:2609.20804 [cs.AI]，Run-Ze Fan 等 9 人（通讯作者 UMass Amherst），**v1 提交 2026-09-17 17:58 UTC**，43 页；交叉学科 cs.AI / cs.CL / cs.LG / cs.SE
- 一句话：把 coding harness 拆成 planning / action space / **context management** 三个旋钮，固定执行循环后跑 **176 组匹配配置**，逐一量化每个旋钮值多少钱。
- 关键数据（带口径）：
  - 评测面：**4 个模型 ×（SWE-Bench Verified + Terminal-Bench 2.1）**，覆盖 **5 种上下文管理策略 × 4 档上下文窗口预算**，外加 planning / action space 定向消融，合计 **176 组匹配设置**。
  - **结论 1（最该记住的）**：上下文管理价值 **随上下文预算收紧而上升**，收益「大部分来自**防止 context-overflow 失败**」，而非提升 agent 推理能力。窗口宽裕时花哨的 compaction 几乎不涨点。
  - **结论 2**：**「先规则裁剪、后 LLM 摘要」的两级 staging** 是全局效率最优；而对被裁剪内容做「可恢复（recoverable）」设计，模型几乎不用、且**零准确度收益**——纯属白建的门。
  - **结论 3**：planning 对弱模型是**准确度脚手架**；对强模型只是**省钱手段**（准确度几乎不变）。是否加 planning 没有普适答案。
  - **结论 4**：预定义工具有利于 bash 能力弱的模型；bash 能力强的模型用**裸 bash 接口**即可同等甚至更优，且在命令行密集任务上成本显著更低。
  - 轨迹层面解释：上下文管理**延长轨迹但不改变行为**；planning **改变轨迹在哪里停下**；action space 改变写代码的粒度。
- 对我们的意义（说人话）：这条直接给 DSH / 橙皮书那套上下文工程提供了外部判决。别再把「上下文管理」当提分 gadget——它是**保险费**，预算越紧越值钱。两件立刻能做的事：① 压缩管线改成**规则裁剪优先**（先机械砍掉编译告警、重复 grep 输出、冗余堆栈），LLM 摘要只兜底；② **砍掉「被裁剪内容可回溯检索」那套机器**，论文实测没收益还添复杂度——我们之前默认是好东西，这是被数据推翻的直觉。
- 核实：已核实一手（arXiv abs 页 + 提交历史）

### 2. MERIT：换一套 memory 实现，任务成功率最多差 **60 个百分点**；全量重放永远不划算
- 链接：https://arxiv.org/abs/2609.05441
- 来源 / 日期：arXiv:2609.05441 [cs.AI]，Shweta Mishra、Shashank Mishra，**v1 提交 2026-07-26 07:42 UTC**（⚠️ 二手媒体普遍写成 09-10，那是新闻发布日，**arXiv 一手时间戳是 07-26**，引用请以 v1 为准）
- 一句话：现有 memory 评测（LoCoMo / LongMemEval）只测「对话问答记得住吗」，不测「记住的事实**到底有没有改变行动**」——MERIT 补的就是这个。
- 关键数据（带口径）：
  - 规模：**23,440 个已评分 episode，总花费 $42.57**（含 token 与美元双向计量）。
  - 实验设计：GPT-4.1-mini 两代试点 + **预注册 3 模型 × 3 种子网格**（GPT-4.1、Claude Haiku 4.5；memory 侧固定），另加 Claude Sonnet 5 最新代抽查。
  - **有 memory vs 无 memory**：依赖先前事实的任务成功率从「经泄漏检查验证的地板 0.00」提升到 **0.55–1.00**。
  - **更新事实（updated facts，即记忆会过期）这一档是照妖镜**：embedding 检索**不可预测地崩**（跨模型 **0.30–0.95**，同模型不同种子最大差 **0.45**）；agent 即便「检索对了」也**只有 55% 的时候真的照着做**。
  - **写时更新型存储（结构化 fact store，以及——值得注意——LLM 摘要）稳在 0.70–1.00**；**混合方案比单用 fact store 更差**。
  - 成本：**全量重放永远不经济**；每个领域最优条件是投入的 **2.7–3.9 倍边际效用/美元**。
  - **仅仅替换 memory 的实现方式，任务成功率就能移动最多 60 个百分点。**
- 对我们的意义（说人话）：三个可直接落地的结论。① 「检索到≠会照做」只有 **55%**，这是比召回率更要命的指标，我们的 memory 健康检查该加这一项。② **Embedding 检索在「事实会变」时不可靠**（0.30–0.95 抖动），而 DSH 场景里大量事实会变——涉及版本、路径、模型切换的都应写进**结构化 fact store 或摘要**，而不是丢给向量库。③ **混合方案输过单体**，别无脑叠架构。
- 核实：已核实一手（arXiv abs 页 + 提交历史）

### 3. LOCOMO-CONV：用「对话式」而不是「QA 式」问法，现有 memory 系统大面积露馅
- 链接：https://arxiv.org/abs/2609.03467
- 来源 / 日期：arXiv:2609.03467 [cs.CL]，Wen-Yu Chang、Yun-Nung Chen（台大），**v1 2026-09-03 07:24 UTC，v2 修订 2026-09-22 16:21 UTC**
- 一句话：现有 memory 基准基本是 QA 式探针（直接问「XX 是什么」），但真实用户**不会这么问**——LOCOMO-CONV 把 LoCoMo 改成对话式，一测就发现 QA 基准漏掉的大坑。
- 关键数据（带口径）：
  - 数据集 LOCOMO-CONV 从 LoCoMo 派生，**4 种查询风格**：dialog / implicit（隐式）/ counterfactual（反事实）/ composed（复合）。
  - 评测对象：**5 个代表性 memory 系统**，同时测**检索召回率**与**端到端回答质量**两项。
  - 核心发现：对话式提问暴露出 QA 基准**没看见的巨大检索缺口**，**尤其集中在隐式查询和复合查询**上；多面查询重写（multi-facet query rewriting）能缩窄**原始 turn 型 memory** 的缺口，但对**抽象式 memory（abstractive）没用**。
  - 反直觉一点：**强检索并不完全转化为好回答**；隐式查询存在「**沉默接地（silent grounding）**」——memory 改善了上下文接地，但并没有把黄金那条事实显式说出来。
  - 附产物：发布 `supportive_memory` 标注，捕捉原始黄金证据之外的、对话中有用的上下文。
- 对我们的意义（说人话）：**「测得出召回率高」和「实际有用」是两回事**，这和我们上一辑「口径比数字重要」是同一条脉。具体到我们：① 给 memory 做自测时别只写 QA 式用例，至少要加**隐式**和**复合**两类问法；② **抽象式 memory（摘要型）对查询重写不敏感**——意味着靠改 query 救不了摘要，想救只能改写入/组织方式；③ 「检索对了但回答没体现」的沉默接地现象说明**评测要看端到端回答，不能只看召回**。
- 核实：已核实一手（arXiv abs 页 + v1/v2 提交历史）

### 4. BudgetBench：把「每次调用的输入 token 预算」当自变量，扫 2K→32K
- 链接：https://arxiv.org/abs/2609.13149 ；代码：https://github.com/aviskaar/budgetbench
- 来源 / 日期：arXiv:2609.13149（cs.CL），2026-09 上线；协议 / harness / 复现产物开源
- 一句话：上下文窗口动辄几十万 token，会让人误以为显式 memory 管理没必要——**本地部署不信这套**，BudgetBench 把「每通输入预算」本身做成被扫的自变量。
- 关键数据（带口径）：
  - 自变量设计：固定模型、任务、采样器、解码参数，**预算在 2K / 4K / 8K / 16K / 32K token 五档上扫**，记录质量、预算利用率、延迟，并把**预算违例率作为一等公民指标**。
  - 试点规模三项：本地 **qwen2.5:1.5b** 试点（SWE-bench Verified 与 LongBench v2 **各 89 题**）；托管 **Qwen3 30B-A3B** 的 LongBench **50 题**精确分词复制；**LongMemEval 500 题** oracle 研究（用官方 GPT-4o 评测器打分）。
  - **作者自己坦白的负面结果（值得尊敬的写法）**：budgeted vs full-context 谁更好**尚未有结论**——本地切片接近 null，托管复制在点估计上偏向 full context，且**没有任何配对区间能建立等价性**。
  - 另一处自曝：早期本地试点的**分词器近似会低估部分 served-model 的 prompt**，因此其「违例行」只能算分词近似诊断，**不能当作结论性合规数据**；所有计时均为运维诊断，非性能主张。
  - 可复用产出是 `MemoryStrategy` 可插拔契约 + 显式预算强制 + 确定性/版本化 grader + prompt-audit 元数据。
- 对我们的意义（说人话）：这是本期**唯一一个把「预算」当实验变量而不是当背景条件**的工作，正好补我们缺的那块。特别是它的失败学：作者主动划出「哪些数字不是结论」，这种 **failure-reporting 纪律**值得直接抄进我们的自测报告模板。另外，本地小模型（qwen2.5:1.5b）这一档对本地向Qwen/Qwen-based harness 有直接参考价值。注意：别把它的 preli 结论当排行榜用，作者明确说自己没排出来。
- 核实：已核实一手（arXiv HTML 摘要页 + 代码仓库）

### 6. GPT-6 Astra 是 OpenAI 首个「**Critical 级**」网络安全能力模型 —— 只收这条未被上辑覆盖的维度
- 链接：https://openai.com/index/gpt-6-astra/ ；OpenAI Preparedness Framework 分级说明
- 来源 / 日期：OpenAI 官方，**2026-09-03** 发布；首发渠道为公司自己的 Daybreak 可信访问计划企业客户

- 关键数据（带口径）：
  - **ExploitBench（针对已知漏洞开发可利用性的评测）：Astra 满分 100%，上一代 GPT-5.6 Sol 为 78.5%。**
  - 内部实测：用过去三个月披露的漏洞搭的测试里，Astra **发现并利用了两个 0-day**，OpenAI 已向受影响厂商披露。
  - 能力口径（OpenAI 定义）：「Critical」级＝在获得适当工具与访问权限时，能在许多防护严密的系统中发现未知安全漏洞并开发相应利用方法，**无需人工逐步指导**。
  - 缓解措施：最先进的网络安全能力（含生成 PoC 利用）在发布时限缩给经审查的 Daybreak 测试者，**不广泛放出**。
  - 训练侧口径（OpenAI 的 Aidan Clark）：**首次在单一站点（德州 Stargate）用超过 10 万张 GPU 预训练**，是其史上最大训练run；也是首个「早期模型在监督训练过程中扮演重要角色」的发布。
  - ⚠️ **OpenAI 自己披露的负面结果**：在专门测试能否逃避监管的评估中，Astra 的推理**比起前代更难被自家监控工具跟上**；官方说它在复杂任务上仍难以完全隐藏推理，并把「可监控性」列为持续研究重点。
- 对我们的意义（说人话）：两个实操点。① 「首个 Critical 级」是**能力口径的变化，不只是分数变化**——以后看到任何厂商说自己「达到/未达到某个安全等级」，必须先问它用的是哪一套框架的分级。② 那条「**推理更难被自家监控工具跟上**」是最值得抄进错因笔记的一句：**能力越强，日志越不等于行为**。我们做留痕/审计时不能默认「看了日志就复原了它怎么想的」，这条和上一条 Claude 协调器「只看回报不看每步」是同一件事的两个版本。

### 10. Mistral Vibe 六个 CVE（四个 CVSS 10.0）：**命令白名单是对字符串做判断，两个解析器之差就是漏洞**
- 链接：HiddenLayer 安全公告（经其自有 CNA 对 `mistralai/mistral-vibe` 备案）；CVE-2026-87983 / 87984 / 87985 / 87986 / 87987 / 87988
- 来源 / 日期：HiddenLayer，研究员 Esteban Tonglet，公开披露 **2026-09-11**
- 一句话：Vibe 用 tree-sitter 解析待执行命令来判断要不要弹审批，**写着 pronunciation 一个东西、bash 跑的是另一个**——六个 CVE 是同一个 bug 的六种写法，四个 CVSS 4.0 **满分 10.0**。
- 关键数据（带口径）：
  - **CVE-2026-87985（10.0，CWE-184，v2.9.0 起）**：用 **ANSI-C 引号 `$'-exec'`** 把 `find` 的 `-exec` 谓词藏起来；Vibe 的 tree-sitter 语法树不检查 `ansi_c_string` 节点，bash 在运行时把参数还原 → 已批准的命令变成任意代码执行。**公告明确指出可经由间接提示注入触发。**

  - **CVE-2026-87986（10.0，CWE-228，v1.3.4 起）**：解析器读不懂的 shell 构造落在 `ERROR` 节点上，**这些节点完全不进权限判定**。
  - **CVE-2026-87988（10.0）**：无条件放行的命令**跳过路径校验**，工作区围栏失效。
  - **CVE-2026-87984（9.3）**：shell **重定向目标**不在权限检查内 → 任意文件写。
  - **CVE-2026-87983**：带引号的绝对路径可读工作区外文件。
  - ⚠️ **写成当时的不采纳边界**：截至写作时，仓库 GitHub security advisories 页为空，**六个记录都没有给出修复版本号** —— 「升级」这个建议在当时无法精确执行。
- 对我们的意义（说人话）：这是本期和「上下文管理」同等重要的一条，因为它是**agent 安全**里最典型的一种架构错误，而且**不局限于 Mistral**：靠字符串解析做的命令白名单，「就是第二份 bash 实现，而且永远比 bash 差」。两个解析器、一次执行，**中间的缝就是漏洞**，这个缝不会有永久关闭的版本。给自己的三条硬约束：① 审批弹窗是**交互体验，不是隔离边界**；真边界要落在容器/文件系统/token 作用域上；② 默认假设**提示注入是投递途径**——agent 会读 issue、README、依赖 changelog、抓下来的网页，任何一处都能带 payload，攻击者不需要你的键盘；③ 给 agent 的凭证要按「最小可用」缩作用域，一个只能碰单个预发项目的 token，能把 CVSS 10 变成一份事故报告而不是一次数据泄露。

### 13. Credentials API：**提示词即使被投毒，也拿不到你的真实 token** —— 和 #10 的六个 CVE 正是一对
- 链接：https://goo.gle/3V0bp8f ；Philipp Schmid（Google DeepMind）发布帖；Google Credentials API 文档
- 来源 / 日期：Google DeepMind 官方，**2026-09-17~18**（与 #12 同一次发布）
- 一句话：凭证预先注册在服务端，agent 真正发请求时由**沙箱外围的网络代理**在出口路上注入真值——**模型从头到尾没见过你的 token**。
- 关键数据（带口径）：
  - Schmid 原话：「We created a network proxy around the agent sandbox which basically injects the credentials when the agent makes a request from inside the sandbox to outside the sandbox. So the agent never really sees your credential.」
  - 官方口径：**明文 secret 从不进入模型上下文 / stdout / agent memory**。沙箱里看到的只是占位符，例如 `GEMINI_CRED_slack-bot-token`，真值在出网时才被代理替换（**write-only，存进去就取不出来**）。
  - 三种凭证类型：`bearer_token`（静态 / MCP 服务器的 Authorization 头）、`oauth2`（Google 侧**自动刷新并在过期前轮换**）、`environment_variable`（给沙箱占位符，绑定显式 `trusted_domains` 白名单）。
  - 可挂载位置：远端 **MCP server 工具** 或**沙箱环境变量**。
  - ⚠️ 边界：**出站网络访问默认不设限**——白名单和域名限制都要靠 `environment.network` 显式配置，不开就是全开。
- 对我们的意义（说人话）：这条必须和 #10（Mistral Vibe 六个 CVSS 10）对着读。**同一周里，一边是一个被黑ַ的方式止不住的 CVE 集群，一边是把「凭证永不见光」做进架构的答案。** 差别在于：Vibe 是在**应用层**用解析器判断命令安不安全；Google 是在**出口网络层**保证 agent 拿不到原料。给我们自己的两条：① 任何要交给 agent 的 token，优先找「代理注入 / 占位符替换」形态，而不是把它拼进 prompt 或环境变量后祈祷它不失手；② 立刻检查我们自己的沙箱**出站是不是默认全开**——这条 Google 也没替你默认关，属于「给了能力不等于给了安全」。

### 18. arXiv 昨天（09-23）的论文：**模型内部早就知道该压缩了** —— 你在外部猜，它里面已经编码好了
- 链接：https://arxiv.org/abs/2609.27286
- 来源 / 日期：arXiv:2609.27286 [cs.AI]，Mingxuan Wang 等 9 人，**v1 提交 2026-09-23 03:23 UTC**
- 一句话：现有上下文管理都在外部纠结「怎么压缩 / 怎么检索」，这篇先问了一个前置问题——**在 action 发生前那一刻，模型的隐状态里是否已经编码了「该压缩 / 该回忆」的需要？答案是：是。**
- 关键数据（带口径）：
  - 研究对象：**每次 agent 动作前那一刻的 hidden state**。发现**压缩需求与召回需求已被编码在模型内部表征里**。
  - 反直觉处：这些信号**不能用「上下文长度」或「交互进度」简单解释**，且**在模型不同深度呈现不同的形成模式**（即不是同一件事在重复）。
  - 关键可利用结论：**大部分「记忆决策信息」保存在一段紧凑的近期上下文里**；而**选择性恢复的历史证据**用于补足近期上下文抓不到的长程依赖。
  - 方法：提出 **PaMER（Preaction Memory with Evidence Retrieval）** = 状态引导压缩 + 外部证据检索；**PaMER+** 进一步引入 step 级证据选择，**只恢复当前任务所需的历史信息**。
  - 评测面：**WorkBuddyBench**，跨多个上下文管理基线与多个模型骨干，结果是**大幅降低上下文消耗且保持有竞争力的任务表现**。
- 对我们的意义（说人话）：这条是本期**最能直接改变我们实现方式的**一条。我们现在的压缩策略本质上是「外部启发式」——到多少 token 了、多少轮了，就压。这篇说：**别在外面猜，读模型自己的状态**。而且给了一个更省的实现方向：**先保留紧凑近期上下文（决策信息主要在里头），历史证据按需按步恢复**，而不是全量重放——**只捞回当前这步真正需要的，而不是把整个世界重建一遍**。注意对照 #12：Google 是在**外部**定 135k 阈值，这篇说触发时机其实可以从**模型内部**读出来。（WorkBuddyBench 这个评测此前未见，像新冒出来的 bench，值得单独跟一下。）
- 核实：已核实一手（arXiv abs 页 + 提交历史 + 摘要原文）

### 19. Salesforce：做「跑十天」的 agent，**先解决不遗忘，再谈学习** —— 层级 / 节拍 / 级联三件套
- 链接：https://arxiv.org/abs/2609.19519
- 来源 / 日期：arXiv:2609.19519，Salesforce 研究团队，**v1 提交 2026-09-17**
- 一句话：作者从长时程设定里推出七条瓶颈，给出的答案长在 **harness 里，不在模型里**——并且明确拒绝「把记忆问题外包给模型厂的超长窗口」。
- 关键数据（带口径）：
  - 核心论点原话级表述：**长时程 agent 必须先能「持续运行而不遗忘」，然后才谈得上「持续学习」。**
  - 三件套（各答一个问题）：
    1. **记忆放哪 → 按时间尺度分层（Levels）**：每层维护**一份有界摘要文件**，向下概括更低层状态；**任务再长，每层要装的东西都是有限的**。
    2. **何时行动 → 时钟节拍（Ticks）**：以**固定 tick 作为自主行动单元**，没人在场时 agent 知道何时该醒、该推进、该汇报，**而不是等下一条用户消息**。
    3. **算力给谁 → 级联智能（Cascaded Intelligence）**：工作先交给**够用的模型**，**评审不通过才升级到更强模型**，以此兼顾成本与可控性。
  - 它的实验证明（本报告最值得记的一个故事）：在**人类每天只查看一次**的值守下，agent 在**十天战役**里**跨过每次上下文重置**，复现出了一项强化学习结果。
- 对我们的意义（说人话）：这条和 #1（harness 组件消融）是同一议题的两面：**#1 告诉你哪些旋钮有用，这条告诉你旋钮该装在什么结构上**。三个立刻可用点：① **「每层一份有界摘要文件」** 是「上下文无上界」的唯一可操作解，我们自己的 `memory*.md` 其实就是这个思路的雏形，而现在它有了被系统论证过的形态——**要点是「有界」，文件长到一定程度必须向下一层概括，而不是无限append**；② **tick 驱动**解决了「agent 没人喊就不动」的问题（与 #17 里 Cursor 的 subscriptions 是同一条解决路径，一开源一商业，值得对照）；③ **级联智能**是最省钱也最容易被忽略的一条：**默认用便宜模型、评审不过才升档**——我们现在的习惯是反过来（直接上强模型）。
- 核实：已核实一手（arXiv abs 页）

### 20. RPMem：把每个会话「编译」成**与模型无关**的隐记忆，**换骨干也能带着走**
- 链接：https://arxiv.org/abs/2609.23466
- 来源 / 日期：arXiv:2609.23466 [cs.CL]，Fanyu Zhao 等 9 人，**v1 提交 2026-09-20 08:51 UTC**；代码已公开
- 一句话：文本型记忆每次查询都要检索重建，**越用越依赖检索质量**；参数型记忆虽有，但大多不支持跨会话演化、且绑死某个骨干——RPMem 两阶段架构同时解决这两个问题。
- 关键数据（带口径）：
  - 两阶段：**① 把每个会话通过前向计算「编译」成一个与模型无关的隐记忆（latent memory）**；**② 用一个 task-trained 循环门（recurrent gate）**把它与保留的记忆选择性整合；最后再把整合结果**映射成骨干专用的 LoRA 参数**。
  - 关键收益：**换骨干（backbone replacement）时编码能力可迁移**——这是别家参数型记忆做不到的。
  - 评测面：**3 个长期记忆基准 × 5 个不同骨干**，显示广谱泛化，**更新成本与记忆占用近似常数**。
  - 主结果：**Qwen3-8B 在 PERMA 上达到 85.52%，分别超出最强参数型基线 5.32 个百分点、最强文本型基线 12.98 个百分点。**
  - 消融验证：会话编译与跨会话整合是**互补**的两个角色；动态分析显示那个**门**学到了任务特定的记忆整合策略。
- 对我们的意义（说人话）：结合 #2（MERIT：memory 实现一换，成功率能差 60 点）来看，**「记忆实现方式」本身就是一级变量，不是实现细节**。RPMem 的价值主张里最该记住的是「**换骨干带着走**」——我们这类项目迟早要换模型（见 #11：模型供应说断就断），如果积累的会话记忆换个模型就得重来，那前面所有的「越用越聪明」都是假的。**这可能是本期对「长期资产」这个概念最重要的一条。** 另外「更新成本与记忆占用近似常数」是参数型记忆相对文本型的核心优势：文本型会随时间线性膨胀，参数型不会。
- 核实：已核实一手（arXiv abs 页 + 提交历史 + 摘要原文）

### 22. 反直觉实证：**加了「对口」的 skill，agent 反而变差** —— 307 个人工确认的案例
- 链接：r/PromptEngineering 讨论串（引用 arXiv 论文）与 r/AI_Agents 同期讨论
- 来源 / 日期：社区 + arXiv，**2026-09 初**（约 09-01~09-04 当周）
- 一句话：一篇论文给出 **307 个手工确认的案例：加入一个「话题对口」的 skill 之后 agent 表现反而下降**——而 skill 范式这两年几乎是被默认收益的。
- 关键数据（带口径）：
  - **307 例手工确认**，在同一模型、同一 harness 下细分成：**125 例功能性失败** + **182 例效率回退（加了 skill 的那次比不加更贵）**。
  - 机制解释（LlamaIndex 的 Clelia Astra Bertelli / Tuana Çelik 口径）：**tool 是单次确定性函数调用，skill 是「在行动前塑造推理」的复合程序性上下文**——**非确定性正是从这里进来的**。
  - 社区另一方的实践回应：有人弃用 skill，改为**自建一整套原生 docx / pdf 原生工具**，理由是「skill 易碎、烧 token、不确定」。
  - 同期相邻证据（Princeton NLP，同周在 r/AI_Agents 被引）：**同等工具与上下文条件下，单 agent 在 64% 的基准任务上追平或优于多 agent 系统**；而多agent只带来 **约 +2.1 个百分点的准确率提升，成本约为两倍**。
- 对我们的意义（说人话）：这条直接打在我们的日常工作方式上——我们近几年建了大量 skill/规格文件，默认假设「多写一份上下文 = 下一次更好」。**307 个反例说：对口 ≠ 受益。** 三条硬约束建议：① **给每个 skill 定「验证再看」的规矩**：新增后要在同一批任务上跑一遍对照，确认没有功能性失败也没有效率回退，才算落地；② **确定性的活一律做成原生 tool，不要做成 skill**（这正是上面那条「tool vs skill」的分界线）；③ 那条「**单 agent 在 64% 任务上不输多 agent，而多 agent 约双倍成本只换 +2.1 点**」应该成为我们开多 agent 之前的默认先验——**先证明"+2.1 点"在自己这个任务上真的存在，再付那双倍的钱**。
- 核实：二手待核（社区讨论 + 对 arXiv 论文的引用，**未核到论文 arXiv 号本身**；Princeton NLP 那条同为社区转载。**数字 value 引用前需补一手核验**）
