## 三、Web 接入

- [1 分钟，让你的网站充满吸引力！保姆级 Live2D 网页教程](https://juejin.cn/post/7439232445470359552) — 稀土掘金 · **程序员鱼皮** · **2024-11-20**（WebFetch 页面所见，7,100 阅读） · 一行 `<script src=".../live2d-widget@latest/autoload.js">` 就能挂上看板娘，但作者点破了这行代码的代价：**脚本默认从作者自己的远程服务器拉模型列表和对话内容**，想自定义就得改源码重新 `npm build`；他给出的做法是复制模型定义文件改成读本地 `model_list.json`，配 `isLocalModel: true` + `modelsPath` + `modelListPath`；另外一个必踩的坑：**改成本地后双击 html 直接打开会失败**，浏览器限制 file:// 加载本地资源，必须起一个静态服务器（`python3 -m http.server` 也行）。 · 上辑收的两条 Web 接入讲的是「三条路线怎么选」，这条讲的是**「用最省事的路线之后，怎么把它从别人的服务器上摘下来」**——对要发行商业作品的人是刚需（不能让看板娘的模型和文案依赖第三方服务器，既是可用性风险也是合规风险）。「本地化后必须起 HTTP 服务」这条也能省掉半小时对着空白页面找 bug 的时间。

## 四、授权与商用（官方中文一手）

- [无偿提供素材使用授权协议（中文译本）](https://www.live2d.com/eula/live2d-free-material-license-agreement_cn.html) — Live2D 官方 EULA（中文） · 未核实（协议文本页无发布日期） · 把「官方免费素材到底能不能进我的商业游戏」逐条钉死：素材分四类授权（免费软件 / 代码样本 / **Live2D 原创角色** / **合作角色**）；关键分界线是 1.22/1.23 条定义的「一般用户 / 小规模企业」＝**最近一个会计年度销售收入不足 1,000 万日元的个人、学生、团体**；在这个身份下 **Live2D 原创角色「可用于任何营利或非营利目的」（2.1.3.1）**，而**合作角色「不得出于营利目的使用」（2.1.4.1）**；四类素材一律**禁止转发、禁止变更/改编/翻译、禁止反向工程、禁止转让权利**（第 4.1 条）；派生作品有义务按下载页的「利用条件」标示著作权（2.1.5）。 · 这是本轮**最硬的一条**，因为它把上两辑一直在绕的问题直接回答了：上辑算的是「SDK 授权要不要钱」（Plan E 个人免费），这辑要问的是另一件事——**「我下载的那个官方示例模型本身，能不能放进我要卖的游戏里」**。答案是分角色的：**原创角色可以，合作角色不行**，而且不能改、不能转发（只能作为派生作品的一部分发布）。对个人/小规模开发者来说，等于「第一个模型用官方 sample 跑通再发行」这条最短路径是**合法**的，但选模型时必须先看清它属于哪一类。

## 三到五条最值钱的发现

**1. 「官方免费模型能不能进我要卖的游戏」这件事，本轮终于有了一手答案，而且是分角色的。**
上两辑一直在算 SDK 授权要不要钱（结论：Plan E 个人免费），但那是**引擎侧**的账；这一辑要回答的是**素材侧**的账。Live2D 官方那份中文 EULA 把素材分成四类，分界线是「最近一个会计年度销售收入 < 1,000 万日元的个人/学生/小规模企业」：在这个身份下，**Live2D 原创角色「可用于任何营利或非营利目的」，而合作角色「不得出于营利目的使用」**；四类素材一律禁止转发、禁止改编。翻译成人话：**第一个模型直接拿官方 sample 跑通并塞进商业 Ren'Py 作品，是合法的——但你必须先看那个模型是「原创角色」还是「合作角色」**，且不能把它单独发出去。对小团队来说，这等于把「先跑通链路再换自己角色」这条最短路径的合规风险归零了，代价只是下载前多花两分钟看清分类。

**2. 建模报价从「听说几千块」变成了可以逐项核对的明细单，而且拆图精细度本身就是计价单位。**
米画师两个橱窗（￥2631 / ￥3157）把价格拆到了部件级：头部九轴 X 30-45° / Y 10-15°、3×3 或 3×4 口型、全身三段物理、第二套衣服 +1000、进阶 VB 口型 +200……其中「图层 350 以内，每超 100 图层加收 15%」这一条最有信息量——**它证明了拆图的精细度是被当作商品计量的**，正好和上辑那位画师「画 7 小时、拆 14 小时」的工时账咬合：贵的不是画画，是拆。另外工期分段表（布点透视 7-10 天 + 物理调试 10-15 天，占 30-45 天总工期的三分之二）直接指出了**自学的时间黑洞在哪两块**。退款规则「做完物理不退」也说明物理是建模里最不可逆的一步——先做物理再改结构等于重做。

**3. AI 全自动链路出现了正面证据，而且拆图这步有免登录的免费在线入口，不碰显存门槛。**
上一辑那篇 note.com 用 29 部件 / 23 次测试亲手证伪了「一张图全自动出成品」，本轮 `whalegirl-pet` 这篇**跑通了同一条路**：AI 立绘 → See-through 15 层 → psd2live 自动绑骨 → .moc3，作者明说「没有任何手工美术操作」。两篇合起来才是完整判断——**差别不在工具，在素材**：那篇的失败触发条件是「插入真实立绘」（长发套不进短发、眼嘴位置对不上），这篇的成功前提是 AI 生成的正脸对称立绘。最关键的一条实操信息是：**See-through 有 HuggingFace 的免费在线 demo 且免登录**（768 分辨率约 89 秒），这直接取消了上一辑「ComfyUI-See-through 显存门槛未核实、先确认显卡再决定」这个阻塞结论——**不用显卡也能先试**。代价和约束都很清楚：psd2live 要 JDK 21；`mouth` 图层必须是最大张口原图；`eyelash` 只能含上睫毛。

**4. 引擎侧的坑是「三个版本号必须同时对齐」，中文圈终于有人把失败全过程贴出来了。**
Unity 那条 2020 年的帖子把三版本不匹配演了一遍：3.1 模型 + Unity 2019.4 → `live2d unloaded` 白板；换 Unity 2017 → 另一种错、console 里只报两个「当前点击模型文件的时间」（**报错长得跟 Live2D 毫无关系**）；最后 SDK 4-r.1 + CubismEditor4 + Unity 2017.1 + 模型重导出才通。Ren'Py 那条则给了一个官方手册绝对不写的坑：**runtime 文件夹里的东西拷进模型目录后必须把 runtime 文件夹本身删掉，否则报错**。这两条共同给出了诊断顺序：**先怀疑版本不匹配，再怀疑文件结构，最后才怀疑自己的操作**——以及一个反直觉的预警：报错信息可能和真正的病因完全无关。

**5. 「AI 驱动角色」这条热闹的线，对本机这个场景是走偏的。**
CSDN 那篇 AI 虚拟伴侣指南写得不错（ASR/LLM/TTS/Live2D 五模块、Ollama 可接、每个库都真实存在），但它自己给出的硬件门槛就说明了问题：**推荐 GTX 1060 6G 起、3B 模型约 4GB 显存**——这是一套**运行时**方案。而单机视觉小说的对话是写死在脚本里的，发行包里不需要一个实时 LLM。详见下一节的逐条判定。

## AI 相关的可直接落地的改动建议

本轮 AI 相关中文内容命中 2 条，**都读了正文**（whalegirl-pet 全文、CSDN 那篇取到前 3 节）。逐条判定：

### ✅ 采纳一：把 See-through + psd2live 当成「第一版粗模生成器」，而不是成品生成器

**改什么**：在现有立绘工作流里插一步——出完立绘后，**先用 See-through 的 HuggingFace 免费在线 demo 跑一遍分层**，再看要不要人工修。

**怎么改**（按可验证的顺序）：
1. **只跑在线 demo，不装本地环境**。`24yearsold/see-through-demo`（文档说免登录），768 分辨率约 89 秒出 15 层 PSD。**这一步不需要显卡、不需要改本机任何配置**——这是它能落地的前提。
2. **提前装 JDK 21**（免安装 zip 即可）。psd2live 的 CLI 是 `gradlew run --args="--input X.psd --output Y --lang zh"`，本机如果有的是 JDK 17，这一步会直接卡住。
3. **把两条硬约束写进立绘规格书**：`mouth` 图层必须是**最大张口**的原图；`eyelash` 图层**只能含上睫毛**。这两条不满足，自动绑骨出来的模型会「看起来没有嘴」或「闭眼撕裂」。
4. **把 psd2live 的产出定位为「草稿」，不是成品**。文档自己说 `.cmo3` 可以在 Cubism Editor 里打开手工精修变形器和动作曲线，因为「PSD2Live 生成的绑定是自动拟合的，手工调过会更自然」。

**验证方式**：
- 用同一张立绘跑两次（一次原图、一次按规格改过嘴部的图），对比 Cubism 里 `ParamMouthOpenY` 从 0 拉到 1 的表现——**验收标准是「=0 时不消失、=1 时张得开」**。
- 导出 `.moc3` 后先丢进 Cubism Viewer 看能否加载，再决定要不要进 Ren'Py（沿用上辑 `has_live2d()` 的降级写法）。

**⚠️ 商用前必须先解决的一件事**：psd2live 是 **GPL-3.0**（上辑已标注）。用户做的是**商业**视觉小说，用它生成的文件进发行包之前，**必须先确认 GPL-3.0 对 `.moc3` 这类产出物有没有传染性**。这条不能跳过，也不能靠问 AI 得到答案（房规 M-0028）。若判不清楚，退路是：**只用 See-through 拆层（它不参与绑骨、产出的是 PSD），绑骨这步回 Cubism Editor 自己做**——这样 GPL 的东西根本不进入产物链。

### ✅ 采纳二：B站/国产 TTS 只用于「开发期临时配音」

CSDN 那篇里 `edge-tts`（免费、中文自然）这一条对单机视觉小说是**有用的**，但用途要限定：**只在开发期给对话打临时音轨**，用来校准文本节奏和演出时长，正式配音再换人声。理由：视觉小说的配音是**离线预渲染**的，不存在「运行时 TTS」这个环节，所以 TTS 在这里是**制作工具**而不是**游戏功能**。

### ❌ 不采纳：LLM 实时驱动角色（AITuber / 口型同步流水线）

**没用，因为**三条理由，任何一条单拿出来都足够：
1. **场景不成立**。第一款商业视觉小说的对话是**预先写好的脚本**，玩家读的是作者写的文本，不是模型生成的文本。装上 LLM 只会增加不确定性（同一句台词每次演出不同、可能说崩），而视觉小说恰恰要的是**可复现的演出**。
2. **成本不成立**。那篇自己给的最低门槛是 GTX 1060 6G / 3B 模型约 4GB 显存；用户是 **16GB 内存**（内存 ≠ 显存），显卡型号未确认。把这套塞进发行包，还要额外承担模型体积、运行时稳定性、以及玩家机器上的兼容性三重负担——**收益为零，成本全担**。
3. **口型同步在 Ren'Py 上也不成立**。那篇讲的「音频能量归一化 → 驱动 `ParamMouthOpenY`」是**运行时改参数**的做法，而 Ren'Py 的 Live2D 只能播**预先做好的 motion / expression**，无法在运行时改单个参数（上辑 §五已核实）。真要做口型，正确做法是在 Cubism 里把口型做成 motion 或表情，按对话行切换——**是建模期的活，不是运行时的活**。

如果要保留这条线的价值，唯一值得做的是把它当**开发期的原型工具**：用 Ollama + edge-tts 快速把对话跑一遍听节奏，确认文本长度和停顿是否舒服，然后**把结果固化回脚本**。这跟采纳二是同一件事，不需要额外的 AITuber 框架。

### 一句话总结

本轮 AI 侧能落地的只有**「用免费在线 See-through 拆层 + 用 psd2live 出粗模 + 回 Cubism 手工精修」**这一条，而且**商用前必须先过 GPL-3.0 这一关**；至于「让 AI 实时驱动角色说话」——对单机视觉小说是**走偏了**，省下这个时间。
